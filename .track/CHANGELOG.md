## 2026-08-08 — Daily midnight widget refresh (committed `81b7ab2`, pushed)

User picked "Midnight widget refresh" from the next-feature pitch. Placed widgets (voice/minimal/extend) previously only re-read their DataStore state when the app was paused/opened, so after midnight a never-opened widget could keep showing yesterday's chart / "Left today" until the user opened the app.

- **New `widget/WidgetRefreshScheduler.kt`** (`object`): `schedule(context)` / `cancel(context)`, request code `200`, action `com.danilkinkin.buckwheat.WIDGET_REFRESH`, trigger = next **00:05**, `PendingIntent.FLAG_UPDATE_CURRENT or FLAG_IMMUTABLE`. **Key decision: `setWindow(RTC_WAKEUP, trigger, 10 min, pi)` instead of `setRepeating`** — on modern Android `setRepeating` is inexact with a huge window (~+18h observed in `dumpsys alarm`), which can defer the refresh far past midnight; `setWindow` bounds the delay to ≤10 min past 00:05 without requiring `SCHEDULE_EXACT_ALARM` (denied by default on API 33+). Because `setWindow` is one-shot, the receiver re-arms the next day's alarm after each fire.
- **New `widget/WidgetRefreshReceiver.kt`**: `BroadcastReceiver` (manifest, `exported="false"`) that, on `ACTION_REFRESH`, calls `WidgetReceiver.requestUpdateData(context, …)` for Extend/Minimal/Voice (identical path to `Application.onActivityPaused`), then `WidgetRefreshScheduler.schedule(context)` to re-arm. Deliberately does **NOT** replicate `SpendsViewModel.runChangeDayAction`'s daily budget fold (ASK mode needs a UI dialog; the fold is `changeDayMutex`-guarded) — it's a re-read + re-render only.
- **Wiring**: `Application.onCreate` calls `schedule()` (covers normal runs + re-install); `ReminderBootReceiver` also calls `schedule()` on `BOOT_COMPLETED` (alarms don't survive reboot). `RECEIVE_BOOT_COMPLETED` permission already present.
- **Verify**: `spotlessApply` + `assembleDebug` + `testDebugUnitTest` (**153 tests**, 0 failures). On API 36 emulator: `dumpsys alarm` shows `RTC_WAKEUP … WIDGET_REFRESH … window=+10m` re-armed to `2026-08-09 00:05:00`. End-to-end proven with a temporary +90s trigger + temp logging: `onReceive` fired → all three `updateAction` broadcasts sent → Glance `SessionWorker` ran (widget re-render) → re-armed. Pitfalls hit: (1) shell `am broadcast` **cannot** deliver to an `exported="false"` receiver (silent `result=0`, no `onReceive`) — to test the chain the receiver was temporarily `exported="true"`, then reverted; (2) the emulator defers inexact alarms under Doze/app-standby (alarm stays pending past `when`), so the temp trigger test only completes once the device is ACTIVE — environmental, not a code issue; (3) a transient Glance `No session available for key appWidget-2` SessionWorker error appears right after reinstall and self-heals (widget renders fine). ## 2026-08-08 — Analytics "vs previous" fix: same-day / early-finished / restarted periods (committed `855e240`, pushed)

User reported the "vs previous" comparison "some time is not showing". Both comparison surfaces used a strict `finishDate.before(roundToDay(currentStart))` check, but a period's scheduled `finishDate` is stored at end-of-day (`roundToDay(finish) + DAY - 1000`), so:

- **Root cause**: a previous period finished early *on the same day* the current period starts — or a mid-period restart archives the old period with a scheduled `finishDate` still in the *future* — never satisfies `finishDate.before(start)`, so the comparison silently vanished.
- **Fix**: `CompareToLastPeriodCard.kt` gains `effectiveFinishDate(period) = actualFinishDate ?: finishDate` (day-granularity: a period is "done" on the calendar day its `actualFinishDate`/`finishDate` lands), and both `findPreviousPeriod` and `SpendsTrendCard.previousPeriodBefore` now use `!effectiveEnd.toLocalDate().isAfter(startDay)` instead of the strict millisecond `<` — so an early-finished or restarted period is eligible as soon as its effective end day reaches (not exceeds) the current period's start day. Reset-period restarts with future scheduled finish are no longer hidden.
- **Tests**: 7 new regression cases in `CompareToLastPeriodTest` / `SpendsTrendTest` (same-day contiguous, early-finished eligible, early-finished-after-start ignored, reset-period excluded, `effectiveFinishDate` fallback) → **153 tests** green (was 146). `spotlessApply` + `assembleDebug` green.
- **Known limitation (accepted)**: the compare card is still hidden when the current period has zero spends (the card column is gated by `spends.isNotEmpty()` at `Analytics.kt:143`).

New `SpendsRepository.howMuchSaved()` returns `(R-D)/(restDays + skippedDays - 1) × max(skippedDays - 1, 0) + (D - S)` (or `R - S` on the last day), which equals the old formula for `skippedDays >= 1` but correctly `D - S` for `skippedDays == 0`. `RecalcBudgetViewModel` now displays `howMuchSaved()`. Regression tests `carryForwardStaysPositiveAfterDistributionHandledToday` and `carryForwardStaysPositiveWithLargeBudget` (the real 5000/156.25/150.50/5.75 scenario) added. Verified: 23/23 tests, `assembleDebug`, and on-emulator day-change (clock shifted +1 day → sheet opened showing "Congratulations! You saved ₹5.75" instead of negative)
- **Voice AI failures silently succeeded** — a non-2xx AI response or a failure inside the AI parse produced an empty result that was treated as a successful "no voice" outcome. `VoiceAi.kt` now returns a sealed `VoiceAiResult` (`Success` / `Failure` with truncated error body / `NotConfigured`), `Keyboard.kt` surfaces `voice_ai_error_prefix` in red when the AI call fails, and a new `VoiceAiSettingsSheet` (`VOICE_AI_SETTINGS_SHEET`) submenu on the Settings page holds API key / URL / model (moved out of `Settings.kt`). New strings `voice_ai_title`, `voice_ai_error_prefix`
- **Recurring payments always rendered "$"** — `RecurringPaymentsSheet.kt` formatted template amounts with a hardcoded dollar sign; it now injects `SpendsViewModel`, observes `currency`, and renders via `numberFormat(context, template.amount, currency)` (verified ₹100 row end-to-end)
- **History kept stale rows after editing a transaction** — `History.kt`/`ListAnimation.kt` used a constant `contentHash` per row (`"spent-${tx.uid}"`), so an in-place edit (value/comment/date change) never invalidated the animated row and the old values lingered. Row `contentHash` now includes value/comment/date (day-total rows include the total), so edited rows and totals refresh in place
- **Chat-completions replies were parsed from the wrong JSON field** — OpenAI-style responses wrap the text in `choices[0].message.content`, but `VoiceAi.extractModelContent` read the top-level `content`, so voice AI effectively always fell back to the offline parser. It now unwraps `choices[0].message.content`, reads keys case-insensitively (`optStringIgnoreCase`), and treats prose/garbage replies as a failure → offline fallback (never an empty "success"). Required `testImplementation("org.json:json:20231013")` (JVM stubs Android's `org.json`) and one corrected test assertion
